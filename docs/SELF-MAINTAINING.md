# دليل الصيانة الذاتية

> **ما هذا الملف:** مواصفة صيانة، لا وثيقة تعريفية. كل بند فيه يحمل حالة صريحة — `done` أو `partial` أو `planned` — وإثباتًا يُعاد إنتاجه بالأمر المكتوب بجانبه. بند بلا إثبات يُعتبر غير منفّذ.

## 0. الحد الأساسي أولًا

**المستودع لا يصون نفسه بإنشاء ملف.** الورق لا ينفّذ شيئًا. ما يجعل هذا الدليل ذا قيمة تشغيلية هو أن **سبعة من بنوده مرتبطة بأدوات تعمل فعليًا وتظهر نتيجتها في CI أو في تبويب Issues**. يجوز القول: النظام يراقب ويشخّص ويقترح ويوقف — ولا يقرر.

الفرق بين `done` و`planned` هنا ليس تجميليًا. `partial` تعني: الأدوات موجودة، لكن ما يزال هناك شرط يدوي أو صلاحية غير مفعّلة.

---

## 1. دورة الصيانة المحكومة

```text
Observe → Diagnose → Propose → Validate → Approve → Apply → Verify
```

| المرحلة | من ينفّذها | لا يحدث فيها |
| --- | --- | --- |
| **Observe** | `watch.yml` المجدول + CI عند كل PR | لا كتابة على المستودع |
| **Diagnose** | كل فحص يطبع رمز سبب (`reason=`)، لا جسم استجابة ولا سر | لا طباعة بيانات مستخدم |
| **Propose** | تذكرة واحدة بعنوان ثابت، أو PR من Dependabot | لا إصلاح تلقائي عشوائي |
| **Validate** | `Check and deploy` على كل PR: lint + tests + تغطية + وثائق + أسرار + Chromium + axe | لا يكتمل الدمج بدونها |
| **Approve** | إنسان: مراجعة `CODEOWNERS` + حماية `main` | الآلة لا تمنح نفسها صلاحية |
| **Apply** | الدمج، ثم وظيفة `deploy` وحدها | لا نشر من فرع ولا من force-push |
| **Verify** | `verify` بعد النشر + `watch.yml` أسبوعيًا على الموقع الحقيقي | لا يُعتبر البناء دليلًا على أن الموقع يعمل |

**لماذا `Verify` منفصلة عن `Validate`:** نجاح CI يثبت أن **الحزمة بُنيت**، لا أن الموقع **يُقدَّم**. خطوة النشر قد تنجح ويظل الموقع 404، أو يصبح canonical قديمًا بعد إعادة تسمية. لذلك `verify` يزور الموقع الحقيقي، و`watch.yml` يعيد الفحص أسبوعيًا.

## 3. البوابات التي تحتاج تفعيلًا يدويًا **[المالك]**

لا يمكن لأي سكربت منح نفسه صلاحية. هذه البوابات الأربع مفتوحة اليوم، وتفعيلها هو الفرق بين نظام ووثيقة:

| البوابة | لماذا لا تُؤتمت | كيف تُغلق |
| --- | --- | --- |
| **G1** حماية `main` | تحتاج صلاحية إدارة المستودع | Settings → Branches → حماية `main`: منع force-push والحذف، **Require a pull request**، **Require status checks → `quality`**، **Do not allow bypassing** |
| **G2** مراجعة المالك | `CODEOWNERS` بلا تفعيل لا يُلزم | تفعيل **Require review from Code Owners** |
| **G3** CodeQL | تنبيهات فقط بعد تفعيل من الإعدادات | Security → Code scanning → Default setup → `javascript-typescript` |
| **G4** تدوير المفاتيح | سر لا يُقرأ برمجيًا | وفق `docs/OPERATIONS.md` كل 60–90 يومًا |

**ملاحظة أمانة:** `gh api repos/.../branches/main/protection` أعاد `403 Resource not accessible by integration` وقت كتابة هذا الملف — أي أن الحماية **لم تُثبت مفعّلة**. البند يبقى `blocked` حتى يُثبت العكس بأمر ناجح.

## 4. ما لا يفعله النظام، صراحةً

| ليس ضمن النظام | السبب |
| --- | --- |
| تعديل الكود أو المستودع تلقائيًا | `watch.yml` بصلاحية `contents: read` فقط، بلا auto-merge للمراجعات الكبيرة |
| النشر إلى الإنتاج من فرع غير `main` | شرط `if` صريح في وظيفة `deploy` |
| اعتبار CI دليلًا على سلامة التشغيل | وظيفة `verify` و`watch.yml` تفحص الموقع الحقيقي |
| ادعاء أن الوثيقة نفّذت ما لم يُنفّذ | هذا القسم + حارس `check:docs` |
| حصة مركزية أو مصادقة مستخدمين | يحتاج قاعدة بيانات ومزوّدًا؛ ليس هنا |

## 6. كيف تُحدَّث هذه الوثيقة

1. كل بند جديد يبدأ `planned` مع سبب واضح.
2. لا يُرفع إلى `done` قبل تشغيل الأمر ونسخ مخرجته الحقيقية.
3. `npm run check:docs` يفشل إن اختفى قسم الإثبات أو ظهر `TODO/TBD`.
4. راجع `docs/QUALITY.md` للتفاصيل التقنية و`docs/RUNBOOK.md` للأوامر التشغيلية.
