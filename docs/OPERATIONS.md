# التشغيل الآمن: تدوير المفاتيح والاستدعاء من GitHub

هذه الخطة تفصل بين ثلاثة أشياء:

1. **واجهة عامة ثابتة** على GitHub Pages.
2. **وسيط خادمي اختياري** يحمل مفتاح Groq على Vercel أو Cloudflare Workers أو غيرهما.
3. **GitHub Actions** كأداة تشغيل واختبار وتدوير، وليس كواجهة API عامة للمستخدمين.

> GitHub Actions لا يوفر endpoint عاماً دائماً لاستقبال طلبات مستخدمي التطبيق. لذلك لا يُستخدم كبديل عن Vercel functions أو Cloudflare Workers لتشغيل Groq داخل المنتج. الاستخدام الآمن له هنا: اختبار حي يدوي، فحص بعد النشر، ومهام تشغيلية مقيدة.

## 1. أين توضع الأسرار؟

| المكان | ماذا يضع فيه مالك المشروع؟ | ماذا لا يضع فيه؟ |
| --- | --- | --- |
| GitHub Actions Secrets | `GROQ_API_KEY` لاختبار Groq الحي من GitHub، و`AI_ACCESS_CODE` إذا أُضيف لاحقاً اختبار للوسيط المنشور | لا يضع مفتاحاً في كود المستودع أو في متغيرات `VITE_` |
| GitHub Actions Variables | `GROQ_MODEL` اختياري، لأنه ليس سراً | لا يضع `GROQ_API_KEY` كـ Variable عادية |
| Vercel / Cloudflare Workers Runtime | `GROQ_API_KEY` و`AI_ACCESS_CODE` و`AI_DAILY_LIMIT` و`GROQ_MODEL` حسب الحاجة | لا يعتمد على أسرار GitHub وحدها؛ أسرار GitHub لا تُحقن تلقائياً في runtime الاستضافة |
| GitHub Pages | لا شيء سرياً | أي مفتاح داخل JS أو asset عام يعتبر مكشوفاً |

قاعدة ثابتة: **أي قيمة تصل إلى المتصفح ليست سراً**. `AI_ACCESS_CODE` ليس بديلاً عن مصادقة المستخدمين، بل بوابة مشتركة محدودة المخاطر.

## 2. تدوير `GROQ_API_KEY`

### دورية مقترحة

- تدوير وقائي كل 60–90 يوماً.
- تدوير فوري عند الاشتباه في تسريب، أو عند مغادرة شخص لديه صلاحية وصول، أو عند ظهور استخدام غير متوقع.

### خطوات التدوير بدون كشف المفتاح

1. أنشئ مفتاحاً جديداً من لوحة Groq، باسم واضح مثل `lek-prod-2026-11`.
2. أضف المفتاح الجديد في runtime الوسيط أولاً:
   - Vercel: Project Settings → Environment Variables.
   - Cloudflare Workers: Worker Settings → Variables and Secrets.
3. حدّث سر GitHub Actions:
   - Repository Settings → Secrets and variables → Actions → `GROQ_API_KEY`.
4. أعد نشر الوسيط أو أعد تشغيله حسب المنصة.
5. شغّل اختبار Groq الحي من GitHub Actions كما هو موضح أدناه.
6. اختبر طلباً صغيراً غير حساس من الواجهة المنشورة نفسها.
7. راقب الأخطاء والحصة لمدة قصيرة.
8. احذف المفتاح القديم من لوحة Groq بعد نجاح الاختبار.
9. سجّل تاريخ التدوير واسم المفتاح فقط، ولا تسجل قيمته.

إذا كانت المنصة لا تدعم مفتاحين فعالين معاً، فاستبدل القيمة وأعد النشر بسرعة، وتوقع انقطاعاً قصيراً جداً. لا تضع المفتاح القديم والجديد في الواجهة.

## 3. تدوير `AI_ACCESS_CODE`

الكود الحالي يقبل رمز وصول واحداً، لذلك تدويره يبطل الرمز القديم فوراً بعد إعادة النشر.

1. ولّد رمزاً عشوائياً جديداً، بطول 32 حرفاً أو أكثر.
2. حدّثه في runtime الوسيط.
3. حدّث سر GitHub Actions إذا كان مستخدماً في اختبار وسيط.
4. أعد النشر.
5. شارك الرمز الجديد مع المستخدمين المسموح لهم عبر قناة آمنة.
6. اطلب منهم إدخاله من صفحة الإعدادات؛ الرمز يحفظ في ذاكرة الجلسة فقط.

لا تستخدم `AI_ACCESS_CODE` ككلمة مرور دائمة لخدمة جماهيرية. للإطلاق العام، أضف حسابات/mصادقة وحصة مركزية.

## 4. الاستدعاء من GitHub نفسه

أُضيف سير عمل يدوي: `.github/workflows/groq-smoke.yml`.

خصائصه:

- يعمل فقط عبر `workflow_dispatch`.
- لا يعمل على `pull_request` حتى لا يتعرض لمحتوى غير موثوق.
- صلاحياته `contents: read` فقط.
- يستخدم `GROQ_API_KEY` من GitHub Secrets.
- يرسل prompt صغيراً غير حساس إلى عنوان Groq الثابت.
- يحدد `max_completion_tokens` ومهلة زمنية.
- لا يطبع المفتاح ولا جسم استجابة المزوّد.
- يفشل إذا كان المفتاح غير موجود، أو النموذج غير صالح، أو الاستجابة غير ناجحة.

### تفعيله

1. ادمج هذا التغيير في الفرع الافتراضي حتى يظهر زر التشغيل اليدوي في GitHub Actions.
2. أضف Secret باسم `GROQ_API_KEY`.
3. اختيارياً أضف Variable باسم `GROQ_MODEL`.
4. افتح Actions → Groq live smoke → Run workflow.
5. اقرأ النتيجة: `provider_status` و`groq_smoke=passed` أو رسالة فشل عامة.

### حدود هذا المسار

- هذا اختبار تشغيلي، وليس backend للتطبيق.
- لا تشغله لكل طلب مستخدم.
- لا تضف schedule يومياً قبل معرفة استهلاك الحصة.
- لا تستخدم تعليقات issues أو مدخلات مستخدمين كـ prompt.
- من يملك صلاحية write على المستودع يستطيع تشغيل سير العمل يدوياً؛ راجع صلاحيات المتعاونين.

## 5. اختيار runtime للمنتج

### الخيار A: الواجهة والوسيط على Vercel

- أقل تعديل.
- same-origin.
- لا CORS.
- مناسب إذا كانت خطة Vercel تسمح بنوع الاستخدام، خصوصاً غير التجاري في Hobby.

### الخيار B: Pages + وسيط منفصل

- الواجهة تبقى على GitHub Pages.
- الوسيط على Cloudflare Workers أو Vercel functions أو غيرهما.
- مطلوب عنوان API قابل للضبط في الواجهة.
- مطلوب origin allowlist صريح لنطاق Pages.
- CORS ليس حماية كافية وحده؛ يجب بقاء رمز الوصول، rate limit، سقف tokens، ومراقبة.

## 6. قائمة ما قبل الإطلاق

- [ ] لا يوجد `GROQ_API_KEY` في `src/` أو `public/` أو أي متغير `VITE_`.
- [ ] الوسيط يرفض الأحجام الكبيرة والمدخلات غير الصالحة.
- [ ] يوجد سقف إخراج للنموذج.
- [ ] يوجد rate limit وسقف يومي احترازي.
- [ ] تم اختبار Groq بمفتاح حقيقي مرة واحدة على الأقل.
- [ ] تمت مراجعة حدود Groq الحالية في حساب المالك.
- [ ] تمت مراجعة شروط الاستضافة للاستخدام التجاري إن وجد.
- [ ] توجد خطة تدوير ومالك مسؤول عنها.
